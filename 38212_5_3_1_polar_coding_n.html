Polar 码长 N 的确定

3GPP TS 38.212 §5.3.1 · 动态图解 · n₁ / n₂ 与两个门限实算

一句话：Polar 码的码长 N 必须是 2 的整数次幂， 所以协议要在"够装得下信息"和"别浪费太多"之间挑一个 2 的幂。 挑法是算三个候选、取中间： n₁ 由发送长度 E 定、n₂ 由信息量 K 与最低码率 1/8 定，再夹在 [nmin, nmax] 之间。

一、原文

"The bit sequence input for a given code block to channel coding is denoted by c0, c1, …, cK−1, where K is the number of bits to encode. After encoding the bits are denoted by d0, d1, …, dN−1, where N = 2n and the value of n is determined by the following:
Denote by E the rate matching output sequence length as given in Clause 5.4.1;

If E ≤ (9/8)·2(⌈log₂E⌉−1) and K/E < 9/16
　　n₁ = ⌈log₂E⌉ − 1;
else
　　n₁ = ⌈log₂E⌉;
end if

Rmin = 1/8;
n₂ = ⌈log₂(K / Rmin)⌉;
n = max{ min{ n₁, n₂, nmax }, nmin }　where nmin = 5.
UE is not expected to be configured with K + nPC > E, where nPC is the number of parity check bits defined in Clause 5.3.1.2."

译文（逐句对照）

给定码块送入信道编码的比特序列记为 c0, c1, c2, c3, …, cK−1， 其中 K 是待编码的比特数。编码后的比特记为 d0, d1, d2, …, dN−1， 其中 N = 2n，n 的取值由下述流程确定：

以 E 表示 5.4.1 节给出的速率匹配输出序列长度；

如果 E ≤ (9/8)·2(⌈log₂E⌉−1) 并且 K/E < 9/16
　　n₁ = ⌈log₂E⌉ − 1；
否则
　　n₁ = ⌈log₂E⌉；
结束判断

Rmin = 1/8；
n₂ = ⌈log₂(K / Rmin)⌉；
n = max{ min{ n₁, n₂, nmax }, nmin }

其中 nmin = 5。

不期望 UE 被配置成 K + nPC > E， 其中 nPC 是 5.3.1.2 节定义的校验比特数。

符号读作意思
ck / K输入比特 / 其个数 要编码的比特。PDCCH 里 K = DCI 负荷 A + 24 位 CRC
dk / N编码输出 / 码长 Polar 编码器的输出，N 必须是 2 的幂（第二节）
n—指数，N = 2n。整节要求的就是这个 n
Erate matching output length 最终真正要发多少位（由物理资源决定）。PDCCH 里 E = 108 × AL
⌈x⌉向上取整⌈log₂E⌉ = "不小于 E 的最小 2 的幂"的指数
n₁—候选一：由 E 定的码长基准（第四节）
n₂—候选二：由 K 和最低码率定的上限（第三节）
Rmin = 1/8最低码率 不允许比 1/8 更低的码率 —— 再低只是浪费资源，编码增益已饱和
nmax / nmin硬边界 DCI 与 PBCH：nmax = 9（§7.3.3 / §7.1.4）；UCI：nmax = 10。nmin = 5
nPCparity check bits PC-Polar 的额外校验位。DCI 与 PBCH 都是 0，所以约束简化成 K ≤ E

二、为什么 N 非得是 2 的幂

Polar 编码的核心是反复两两组合：把长度 N 的问题拆成两个 N/2、再拆成四个 N/4…… 一路拆到底。这个结构只有在 N 是 2 的幂时才对齐：

N = 8：　　 ●─┐　●─┐　●─┐　●─┐　　第 1 级：两两异或
　　　　　　 ●─┴┐●─┴┐●─┴┐●─┴┐　第 2 级：隔 2 组合
　　　　　　 ●──┴●──┴●──┴●──┴　　第 3 级：隔 4 组合　→　共 log₂N = 3 级

但物理资源给的 E 不会那么听话（PDCCH 是 108×AL：108、216、432、864、1728，一个都不是 2 的幂）。 所以协议的做法是：先挑一个 2 的幂当 N 编码，再用速率匹配把 N 调成 E。

N > E：要删
多编出来的位打孔（puncture）或缩短（shorten）丢掉。
删太多会破坏 Polar 码的可靠性排序 —— 这正是第四节两个门限要防的事。
N < E：要补
把编出来的位重复（repeat）到够 E 位。
重复是"白送"的能量增益，代价小，所以协议宁可选小 N 去重复。

三、三个候选，取中间那个

n = max{ min{ n₁, n₂, nmax }, nmin }

读法：先取小的（min），再兜底（max）。三个候选各有各的职责：

候选由谁决定它在防什么
n₁E（要发多少位） 防"码长和发送长度差太远" —— 差太远就得大量打孔或大量重复
n₂K 与 Rmin = 1/8 防"码率低于 1/8" —— N 再大也不会让性能更好，纯浪费算力和内存
nmax信道类型 硬上限。DCI/PBCH = 9 → N ≤ 512，UE 侧译码复杂度和存储的天花板
nmin常数 5 硬下限。N ≥ 32，太短的 Polar 码没有编码增益

n₂ 为什么等于 ⌈log₂(8K)⌉

码率 R = K / N ≥ Rmin = 1/8　⟺　N ≤ 8K　⟺　n ≤ log₂(8K)

注意原文写的是 ⌈log₂(K/Rmin)⌉ 向上取整 —— 它不是严格的"不超过 8K"，而是"不超过不小于 8K 的那个 2 的幂"。 因为 N 只能取 2 的幂，向上取整给的是刚够用的那一档。

四、两个门限 9/8 和 9/16 在干什么

这是全节最需要解读的地方。条件是：

如果　E ≤ (9/8) · 2⌈log₂E⌉−1　并且　K/E < 9/16
那么　n₁ 取小的那一档（⌈log₂E⌉ − 1），否则取大的那一档（⌈log₂E⌉）
把 2⌈log₂E⌉−1 记作 N下（比 E 小的那档 2 的幂），条件就好读了：
  • E ≤ 1.125 × N下 —— E 只比下面那一档超出不到 12.5%。 这时选小的 N，只需少量重复就能补到 E；选大的 N 反而要打掉将近一半。
  • K/E < 9/16 ≈ 0.5625 —— 码率不太高。码率本来就高的时候， 再选小 N 会让实际码率 K/N 突破安全范围，宁可用大 N 打孔。
两个条件必须同时满足才敢往小选 —— 一个管"省得划算"，一个管"省得起"。
随 E 变化：n₁ 何时取小的那一档（绿色区间 = 条件成立）
一句话：这两个门限是在"少量重复"和"大量打孔"之间做选择。 Polar 码怕打孔 —— 被打掉的位置会扰乱可靠性排序，凍结位选得就不准了。 而重复只是把同一位发两遍，接收端合并起来纯赚。 所以协议的偏好很明确：能靠重复解决的，就别用打孔。

六、PDCCH 全景：五个聚合等级的 N

PDCCH 的 E 只有五种（E = 108 × AL），K = A + 24。把常见 DCI 尺寸代进去：

N 随 (K, E) 的分布 —— 颜色 = N，竖线 = 五个 AL 对应的 E
看出两件事：
  • AL = 1 / 2 / 4 时都是打孔（N = 128/256/512 分别大于 E = 108/216/432，删 20/40/80 位）； AL = 8 / 16 时变成大量重复（N 被 nmax = 9 顶在 512，而 E 是 864 / 1728， 要补 352 / 1216 位）。转折点就在 AL = 8：N 撞上上限之后，多给的资源只能靠重复消化。
  • AL 每翻一倍，码率 K/E 就减半 —— 这就是聚合等级的意义： 用更多资源换更低码率、更强纠错，而不是换更多信息量。

七、cuPHY 实现：同一件事，用 N 而不是 n

cuPHY 全程不算指数 n，直接算 N（省掉 log 和 pow）：

// polar_encoder.cu:1071  （另一份 CPU 版在 :1101，逻辑相同）
uint32_t        nMin1CodedBits         = roundUpToPow2_nTxBits / 2;      // = 2^(⌈log2 E⌉ − 1)
constexpr float INFO_TX_BITS_RATIO_THD = (9.0f / 16.0f);
if((nTxBits > (9 * nMin1CodedBits) / 8) ||
   ((static_cast<float>(nInfoBits) / static_cast<float>(nTxBits)) >= INFO_TX_BITS_RATIO_THD))
{
    nMin1CodedBits *= 2;                                                 // → 2^⌈log2 E⌉
}

uint32_t nMin2CodedBits = roundUpToPow2Gpu(nInfoBits * MIN_CODE_RATE_INV);   // MIN_CODE_RATE_INV = 8
uint32_t nMinCodedBits  = (nMin1CodedBits < nMin2CodedBits) ? nMin1CodedBits : nMin2CodedBits;

uint32_t nCodedBits = nMinCodedBits;
if(nCodedBits < N_MIN_CODED_BITS) nCodedBits = N_MIN_CODED_BITS;   // 32  = 2^5
if(nCodedBits > N_MAX_CODED_BITS) nCodedBits = N_MAX_CODED_BITS;   // 512 = 2^9

为什么两个条件在 cuPHY 里变成了"或"：协议说"A 且 B → 取小"， cuPHY 反过来问"什么时候不取小"，答案就是"非A 或 非B" —— 这就是德摩根律：
¬(A ∧ B) ⟺ (¬A) ∨ (¬B)
写成"或"的好处是短路求值：第一个条件成立就不必再算那个浮点除法。
cuPHY 把 512 写死了。N_MAX_CODED_BITS = 512 对应 nmax = 9， 只适用于 DCI 与 PBCH。UCI 走 Polar 时 nmax = 10（N 可到 1024）， 这个常量在 PDCCH 链路上没问题，不能直接复用到上行 UCI 编码。

八、那条约束：K + nPC ≤ E

"UE is not expected to be configured with K + nPC > E" —— 要发的位数不能少于信息位数，否则连原始信息都装不下，怎么编都救不回来。

DCI 与 PBCH 的 nPC = 0（§7.3.3 / §7.1.4 明确设 nPC = 0、nPCwm = 0）， 所以约束就是 K ≤ E。代进 PDCCH：

"is not expected to be configured" 是协议的一种特殊说法： 它不是"禁止"，而是"不保证" —— 基站要是真这么配了， UE 的行为未定义，协议不追究。责任在调度器。 cuPHY 侧同样不做这个检查，依赖 L2 保证。
